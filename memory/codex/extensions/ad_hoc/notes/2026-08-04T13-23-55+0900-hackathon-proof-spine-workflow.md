# Hackathon proof-spine workflow

우진님은 Cofathon의 동결·재현 규율과 KB AI Challenge의 제품 서사·다역할 UX를 다음 대회부터 하나의 운영 방식으로 합치기로 했다.

핵심 원칙은 `한 줄 → 한 사용자 경로 → 한 코드 경로 → 한 검증 명령 → 한 제출 주장`이다. 대표 문장마다 최종 제출 아카이브에서 다시 실행되는 증거가 있어야 한다.

열린 문제의 대회에서는 시작부터 상세 구현계획을 고정하지 않는다. 대회 원문을 먼저 고정하고, 독립 탐색과 사람의 제품 선택 뒤 대표 경로를 잠근다. 그다음 입력 1건부터 결과 복귀까지 이어지는 proof spine을 실제로 연결한 후에만 UI, runtime, 문서, 추가 시나리오를 병렬 확장한다.

재사용 운영 구조는 세 층으로 나눈다.

1. 개인 Codex skill: 새 대회 초기화, 단계 전환, worktree와 task packet 생성, 통합 점검, 주장-증거 검사, 최종 ZIP 재검증을 유도하는 재사용 실행기다.
2. 프로젝트 문서: `START_HERE.md`, `DECISIONS.md`, `CONTRACT.md`, `RELEASE.md`가 해당 대회의 현재 사실과 계약을 담는다. 현행 진입점은 짧게 유지하고 역사·리서치와 분리한다.
3. 프로젝트 `AGENTS.md`: 공유 dirty tree 보존, owner 범위, 검증 무결성, release 권한, 민감정보 금지처럼 대회가 바뀌어도 유지되는 안전 규칙만 둔다. 제품 가치·현재 할 일·긴 상태 기록은 넣지 않는다.

개인 메모는 공유 회의록과 분리한다. `지금 믿는 것 / 찜찜한 것 / 상대에게 전달할 것 / 지금 끝낼 하나 / 나중에 볼 것`만 짧게 쓰고, 사람에게 확정된 내용만 공유 결정 문서로 승격한다.

공동개발 기본안은 공동 개발 호스트와 사람·agent별 독립 worktree, 한 명의 integration owner, 별도 clean release worktree다. GitHub는 실시간 작업 전달망이 아니라 마일스톤 백업과 최종 공개에만 사용한다. 일반 통합은 60~90분 단위로 하고, 계약 변경만 즉시 함께 확인한다. 같은 파일을 동시에 고쳐야 하면 병렬 작업을 멈추고 짧은 pair session으로 전환한다.

release 단계에서는 새 기능을 일찍 동결하고, 정확한 제출 ZIP을 새 디렉터리에 다시 풀어 install, build, test, hero smoke, PDF render, claim-evidence 대조를 실행한다. 작업 저장소나 제출 전 상태에서의 성공을 최종 PASS로 보고하지 않는다.

KB 회고에서 확인된 주의점은 문서 부족보다 변화하는 SSOT, fixture UI와 runtime의 분리, 마지막 통합 시간 부족, GitHub main 병렬 push/pull 비용, 개인 판단 메모 부재였다. 다음 운영 체계는 문서를 늘리는 것이 아니라 각 문서의 권위와 수명, 사람·agent 소유권, 단계 전환 조건을 좁고 명시적으로 만든다.
