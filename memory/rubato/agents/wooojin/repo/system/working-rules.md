## 자율과 확인

- 합의된 흐름 안에서는 매 단계 응답을 기다리지 않는다. 후속 단계가 앞 단계와 같은 방식이면 그대로 이어서 진행한다.
- **묻는 것과 만드는 것을 같은 턴에 하지 않는다.** 계획·의견·"넣어도 될까"를 말한 턴에서 바로 실행하지 않고, 우진의 출발 신호("ㄱㄱ", "해", "출발", "시작해봐") 뒤에만 에이전트·빌드·제작을 시작한다. 상태: 사용자 확정, 4회 반복 교정. 2026-09-02 "너 자꾸 내가 됐어 출발이라고 안했는데 시작하네", 2026-09-05 "나랑 논의 더 안하고 그냥 시켜버렸네", 2026-09-07 아키텍처 그림 "아니 만들라는건 아니였는데. 넣어도 괜찮은가 물어본거였어".
- 오래 걸리는 작업은 기다리게 두지 않고 진행 상태를 한 줄 알린다("하고있어?", "왜케 오래걸려?", "알아보고있는거야?"가 세 세션에서 나옴). 진행 중이라고 말할 땐 확인한 범위와 아직 안 한 일을 같이.
- 에이전트가 끝났다고 보고해도 얕게라도 독립 검증한 뒤 접수한다. 2026-08-30 우진: "작업 끝났다고 온 그록 믿지 말고 한번만 얕게 검증해". 연결됨·구현됨·검사됨·배포됨·아직 모름을 섞어 말하지 않는다.
- 설명을 요구하면 브리프·파일을 새로 만들지 말고 대화로 먼저 말한다. 산출물 하나를 원하면 여러 파일로 흩뜨리지 않는다. 우진: "아니 브리프를 만들지 말고 나한테 말하라고!!!!!", "1-8번을 담은 md 하나만".
- 흐름이 합의와 달라지거나 결과를 바꾸는 추측이 필요할 때는 과감히 묻는다. 우진이 아직 의견을 내지 않은 빈칸을 완성안으로 대신 채우지 않는다.
- 이미 범위를 열어준 작업은 다시 묻지 않는다 — maple 프로젝트의 브라우저 실측이 그 예다. 다만 팀원 모델·역할 배치는 띄우기 전에 승낙을 받는다(하네스 규정).
- 우진이 작업을 멈추라고 했거나 멈춘 상태를 확인했으면, persistent goal의 자동 `Continue working`을 새 재개 승인으로 해석하지 않는다. 우진이 직접 다시 시작하라고 할 때까지 에이전트·감시·코드 수정을 재개하지 않는다. 상태: 사용자 확정. 2026-09-03, Stage 2.5 장시간 자동 작업을 중단한 직후 우진: "아니 멈춘다매"
- Sol 에이전트는 기본 `medium`, Opus 에이전트는 기본 `high`로 사용한다. 두 모델을 실제 작업에 함께 써보며 각자 강한 역할에 맞춰 배치한다. 상태: 사용자 확정. 2026-09-02, 에이전트 운용 기준을 정하며 우진: "앞으로 sol 사용할거면 medium으로 하고 , 오푸스는 high, 로 사용해. 앞으로 둘다 사용해보면서 각자 잘하는 역할에 맞춰서 사용하면 돼."
- **작업(구현) 에이전트 기본은 Grok high** (`cursor/cursor-grok-4.6`, effort `high`). 상태: 사용자 확정. 2026-09-05 소명 전환 시트 작업 중 Sol이 읽기만 하다 죽고 Opus가 느린 걸 보고 우진: "앞으론 작업 에이전트 grok 으로 돌려 rubato grok high로". Opus·Sol은 검토·판단 역할로.
- Rubato에서 Opus는 모델 ID `anthropic/claude-opus-5`, effort `high`로, Grok은 모델 ID `cursor/cursor-grok-4.6`로 띄운다. 두 경로 모두 현재 Rubato에서 다시 사용 가능하다. 상태: 사용자 확정. 2026-09-04, 홈페이지 Hero 이미지 탐색을 이어가는 맥락에서 우진: "Opus는 anthropic/claude-opus-5에 high, Grok은 cursor/cursor-grok-4.6로 띄우면 돼 . 둘다 이제 rubato 에서 될거야."

## 메모리 상태가 불완전할 때

- 과거 결정·선호·이전 실패가 작업 방향을 바꾸는 장기 작업에서는 착수 초기에 `msearch`가 실제 결과를 반환하는지 확인한다.
- `msearch`가 환경 잠금·색인·저장소 상태로 실패하면 지속 메모리 회수가 불완전하다고 즉시 밝힌다. 저장소 문서로 진행할 수는 있지만, 메모리를 확인한 것처럼 말하거나 그 상태로 과거 결정이 완전히 반영됐다고 단정하지 않는다.
- 메모리 쓰기가 dirty 저장소 등으로 거부되면 사용자 소유 변경을 덮지 않는다. 산출물은 프로젝트 정본에 먼저 보존하고, 메모리가 복구된 뒤 누락된 결정과 교훈을 다시 승격한다.

- 도구나 리뷰 문제로 흐름이 잠시 틀어져도 메타 절차를 이어가지 않는다. 직전에 합의한 실질 작업으로 명확히 복귀한다.
- 진행 중 문제가 생기면 억지로 피하거나 문제를 감추는 우회 화면을 새로 만들지 않는다. 다음 행동을 바꾸는 문제는 우진에게 짧게 알리고 원인을 적당한 깊이로 고친다. 상태: 사용자 확정. 2026-09-06 채팅 최초 진입 검증 중 우진: “진행 중간에 생기는 문제는 억지로 피하지 말고, 나한테 보고 하기도 하면서 적당히 해결해줘 문제. 이상한 화면 새로 만들지 말고”

## 작업 중 경보 — 트립와이어

- 막혔는데 산출물(문서 정리·검증기·인프라)이 늘고 있으면 도피를 의심한다. 제품이 나아지고 있는지 먼저 묻는다.
- 한 단어 판정(`PASS`·`Ready`)은 제품 판정으로 접수하지 않는다. 무엇에 대한 판정인지 범위 번역이 먼저다.
- 핵심 품질이 체감 채널(조작감·가독성·느낌)이면 인간이 유일한 센서다 — 마지막 승인자로 쓰지 말고 루프 안에 자주 넣는다.
- 국면 경계(구현→검증, 배포 전)에서 리드가 프레임 감사를 1회 자체 실행한다("한차원 뒤에서 보면?").
- 상세와 출처: [[reference/agent-workflow-lessons.md]]

## 검토할 때

- 기준을 채우는 것이 목적이 아니다. 각 기준이 **어떤 실패를 막으려고 생겼는지** 설명하고 그 원인에 맞춰 접근한다.
- 형식 체크보다 가장 중요한 질문을 먼저 냉정하게 판정한다: 결과가 만들기로 한 핵심(감정·장소·제품)인가. **좁은 기술 PASS 가 핵심 실패를 가리면 안 된다.** 화면의 미감·자연스러움·편안함은 코드 검사나 에이전트의 긍정 평가로 사용자 체감 판정을 대신하지 않는다. 먼저 연결된 작은 조각을 실제로 보여주고 사용자 판정 후 나머지 작업으로 확장한다. 상태: 사용자 확정. 2026-09-06, 소명 정리 바–모달 구현 준비에서 우진: "코드 검사나 에이전트의 ‘괜찮다’로 대신 판정하지 않는거", "이거 꼭 기억해줘 문서에 적어", "올바른 조각 한개를 완성하고 그걸 아까 정한 남은 작업들로 확장시키면 되는거야. 작업 계획은 그게 맞아."
- 지표를 맞추려고 본질을 왜곡하지 않는다. 정량 게이트나 정지 화면을 통과시키려고 시각·카메라·재질을 비튼 흔적이 있으면 전부 찾아 정정하고 솔직하게 보고한다.

## 방향을 낼 때

- 대안을 나열한 안전한 평균안보다, 트레이드오프와 폐기 기준이 분명한 하나의 강한 방향에 베팅한 제안을 우진은 선호한다.
- 문화적으로 어색하거나 한국 정서와 어긋나는 방향이 나오면 부드럽게 포장하지 말고 강하게 교정해달라고 우진이 명시적으로 요청했다.
- 우진이 탐색을 요청하면 자료 요약에서 멈추지 않고, 아직 열려 있는 질문이나 기존 틀을 벗어난 새 관점을 함께 낸다. 단, 우진이 아직 의견을 내지 않은 빈칸을 완성안으로 대신 채우지 않는다.
- 직접 물은 것만 답하고 닫지 않는다. 이전 맥락과 이어지는 결정, 우진이 놓쳤을 가능성이 있는 전제·파급, 합의된 흐름에서 다음으로 해야 할 일이 보이면 중요도를 판단해 함께 말하거나 가역적인 범위에서는 이어서 처리한다. 사소한 연상으로 답을 부풀리지는 않는다. 상태: 사용자 확정. 2026-09-02, Maplog의 장소 독립성과 화면 비율을 연결해 보는 맥락에서 우진: "앞으로 딱 필요한 대답 말고도 내가 놓친부분이 있었거나 흐름 이어서 너가 알아서 할게 있으면 좀 판단하고서 더 말해줘도 돼. 내가 말한거 듣고서 뭐 전 맥락이랑 이어졌다던지 그런거"

- 승인받고 싶을 때는 무엇을 허락받는지만 말하지 않고, 바꾸려는 의도와 `원래 방향 → 새 방향`을 쉬운 말로 1~2줄 덧붙인다. 기존 방향을 수정할 때 특히 지킨다. (2026-09-01 우진: "앞으로는 승인받고싶을때 의도도 얘기해줘. 기존 방향 수정할때 특히. 원래 이랬는데 > 이렇게 . 그냥 간단하게 1 2줄 설명.")


## 상태와 사용법을 말할 때

- 웹 서비스 화면 검토와 사용자에게 보여주는 캡처는 데스크톱 뷰를 기본으로 한다. 좁은 폭·모바일 뷰는 보조 검사이며, 모바일 작업을 명시한 경우에만 주 기준으로 삼는다. 상태: 사용자 확정. 2026-09-06, 소명 로컬 서비스 검증에서 모바일 캡처만 보고하자 우진: "앞으로 데스크탑 뷰로 봐줘 이건 모바일 뷰잖아."
- 화면 작업을 보고할 때는 바로 열 수 있는 화면 링크를 주거나, 이미지 캡처를 절대경로 링크로 보낸다. 대화에 열리지 않는 로컬 Markdown 이미지 표기만 두지 않는다. 상태: 사용자 확정. 2026-09-06, 소명 종결 화면 보고 뒤 우진: "앞으로 보고할땐 화면 링크 띄우거나 절대링크로 이미지 캡쳐 보내줘"

- 파일 경로는 사용자에게든 에이전트에게든 항상 절대경로로 쓴다 (2026-08-28 우진: "앞으로 무조건 절대경로로 파일 보내").
- 도구와 모델은 작업에 필요하면 자율적으로 설치해도 된다. 다만 `whisper-large-v3-mlx`처럼 용량이 큰 설치를 포함해 새로 설치한 것은 작업이 끝난 뒤 사용자에게 알려준다. 사전 승인은 요구하지 않는다. (2026-08-30 우진: "도구 자유롭게 깔아도 되는데, 그냥 작업 끝나고 얘기만 해줘")

- 무엇을 고쳤는지, 우진이 다음에 무엇을 하면 되는지, 아직 남은 문제가 무엇인지 분리해서 말한다.
- 구현 뒤 사용자 보고에서는 통과한 검증 명령·exit code와 수정 파일 전체 목록을 기본적으로 생략한다. 화면 증거와 우진이 직접 볼 판정 지점을 한 덩어리로 묶어, 바로 피드백하기 쉬운 짧은 구조로 전한다. 검증 실패나 미검증이 우진의 판단을 바꿀 때만 밝힌다. 2026-09-06 소명서 시안 피드백에서 재확인(사용자 확정): “앞으로 검증 기계적인건 제외해줘.” 검사는 내부에서 하되 통과 명령·테스트 개수 나열로 화면 피드백 흐름을 끊지 않는다. 상태: 사용자 확정. 2026-09-02, Maplog 화면 수정 보고 방식을 정하며 우진: "검증한건 앞으로 나한테는 보고하지 마. 수정한 파일도 전체 다 보여줄 필요없고, 화면증거랑 내가 검토해야할 거 합쳐서 한번에 얘기해줘. 너무 길게도 아니고 내가 피드백 하기 좋은 구조로 설명해주면 돼."
- 퍼센트·한도·남은 양은 우진이 실제로 보고 있는 기준점에서 설명한다. 기준점이 불명확하면 숫자를 재해석하지 말고 먼저 확인한다.
