# 우회 수요 흡수 설계

## 상태와 출처

- 2026-09-01 메이플스토리 패치 사례 분석에서 추출.
- 2026-09-02 우진: “우리 메이플의 교훈을 얻었잖아.”
- 상태: 사용자 확정 교훈 / 지속 메모리 승격됨 / 스킬·전역 배치 검토 중.

## 핵심

> 반복되는 우회는 누락된 primitive의 신호다. 우회법의 위험한 수단을 그대로 기능화하지 말고, 사용자가 위험과 비용을 감수하며 얻으려던 결과를 안전한 일급 capability로 만든 뒤 권한·한도·가격·감사를 붙인다.

관찰된 우회를 다음처럼 분해한다.

```text
관찰된 우회 = 정당할 수 있는 목적 + 위험한 수단 + 제품에 빠진 제약 처리
```

차단을 반복하기 전에 묻는다.

1. 사용자는 실제로 어떤 결과에 돈·시간·위험을 지불했나?
2. 위험한 수단을 떼어낸 뒤에도 정당한 목적이 남나?
3. 그 목적을 제품의 일급 capability로 표현할 수 있나?
4. 공식 경로가 안전성·편의성·복구·감사에서 확실히 우월한가?
5. 공식 기능이 기존 우회를 대체하는가, 결합해 더 강한 악용을 만드는가?

## 설계할 것

- 최소 권한과 역할 범위
- 일·주간 한도와 속도 제한
- 활동·정산·감사 로그
- 취소·복구·분쟁 처리
- 공식 경로가 비공식 경로를 실제로 대체했는지 보는 지표
- 공식 기능과 기존 우회의 결합 악용을 보는 지표

## 제품화하지 않을 조건

- 원하는 결과 자체가 다른 사용자에게 피해를 줌
- 공식화가 사기·스팸·시장 왜곡을 키움
- 소수 사용자를 위해 핵심 경험을 훼손함
- 수요가 아니라 일시적 버그나 가격 오류가 원인임
- 구조 복잡성과 지원 비용이 흡수할 가치보다 큼
- 공식 기능이 비공식 사업자의 생산성만 높임

## 인접 원칙과 차이

- `laws`는 잘못된 상태가 도달 불가능하도록 구현 구조를 바꾼다.
- 이 교훈은 반복되는 사용자 행동에서 누락된 제품 capability를 발견한다.
- `reframing`은 반복 차단이 실패할 때 “어떻게 막나”에서 “무슨 결과를 원했나”로 질문을 전환한다.
- `framing`은 발견한 결과를 현재 대안·비교 가치·피해 지표·실험 계약으로 검증한다.
