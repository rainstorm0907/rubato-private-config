# Multi-screen sequence

Read for several connected surfaces or sessions when local choices may drift apart.
A single screen uses `frontend-creation.md`. This extends that contract; it does not add
an approval after every surface or prescribe a fixed sequence of generated images.

## Keep the experience connected

Use the existing design record for the product's purpose, actual liked/disliked examples
and explicit constraints. Do not force every new reaction into an old vocabulary or add
lists of a fixed length. The user's new experience may change the interpretation.

Before a material new surface, understand its role in the whole path. Keep that role in
existing notes when needed, not a mandatory standalone sentence to approve. Show the
context a person needs to judge it: a single view for local layout, connected states for
flow, normal-speed motion for rhythm, an operable segment for control feel.

Reference examples should change the proposed relationship, not merely supply decorations.
An unfamiliar task may need targeted research; a known one should not restart the whole
research process. Existing images, UI, clips and disposable prototypes are all possible
media. Use the one that exposes the current question with adequate quality.

## Prepare and repair before handing off judgment

The designer owns a coherent first candidate, relevant states, observation and ordinary
in-scope corrections. A generated file or first render is not by itself a handoff point.
If the promised scene is missing, repair it or return the actual scope/capability gap.
Once meaningful user judgment is possible, bring the result and your recommendation
rather than polishing indefinitely or claiming the user's taste in advance.

Continue across surfaces when that is already delegated and the direction remains sound.
Pause only affected work for an explicit checkpoint, a consequential unresolved choice,
a changed commitment, unavailable capability or the assigned budget. User stops remain
binding; silence is not permission for a new direction. A useful partial preview can be
shared without pretending it completes the assignment.

## Carry decisions without freezing methods

Frozen items and Open variables travel with `dispatching`. Protect checkable conditions
with meaningful tests. A preserved reference version does not make every value in it a
constraint on an authorized alternative. Do not alter product scope or explicit locks
without their required approval.

Coupled parts may need to change together to create one experience. Compare coherent
compositions for an overall question and isolate details for a detail question. Neither
whole-winner votes nor mixing favorite parts is mandatory. A new user opinion can open a
previously settled choice; retain the unaffected agreements.

When repeated adjustments fail, inspect the role, composition, rendering approach or tool
that is actually implicated. A rejection count alone does not prove a layer error. Keep
known causes and their fixes in the existing record; do not make the user rediscover them.

## Report what helps the next judgment

Give an accessible result, why you recommend it and the meaningful remaining difference.
Keep machine logs in existing evidence; disclose limits that affect the choice. Distinguish
implementation, actual checks and user adoption without an automatic status ladder or
required report headings. Do not ask the user to review the artifact merely to activate
the builder's own missing quality control.

## Origin of this guidance

The earlier version compared Onjeon's frequent real-screen feedback with Toyrocket's long
intervals of unseen work. Its useful lessons remain: preserve explicit constraints in
execution, observe real artifacts and keep the user involved in consequential experience
choices. That incident does not establish a universal first-render stop, fixed image
count, mandatory role-sentence approval or ban on coherent multi-element alternatives.
