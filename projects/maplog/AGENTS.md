- 실행 승인은 현재 사용자 요청과 CURRENT 단계로 판단한다. 논의·점검·문서 반영이나 방식 제안을 제작 승인으로 넓히지 않는다.

## 한 작업을 닫는 흐름 (사용자 2026-09-30 “일하는 방식부터 똑바로 확립해”, 10/1 밤 “그 방법을 제대로 확립하고 고치는게 너로서 역할”)

사용자는 느낌을 준다(“내가 주는건 느낌이고, 그건 어떻게 만들어나갈지는 너가 잘 고찰해봐야하는거야”). 판단은 리드, 구현은 담당이다(“너가 판단하는게 맞는거잖아 에이전트는 구현만 하는거고”, 10/1 밤). 10/1 밤 지도 탭은 아래 흐름으로 세 바퀴 만에 “이제 좋다”가 됐고, Recap은 11가지를 한꺼번에 바꾸고 숫자로만 받아 9/22 기준판보다 못해졌다(“지금 그것보다도 못하다”).

1. **기준판.** 장면마다 사용자가 좋다고 한 판을 빌드·영상으로 박아 둔다(지금: Recap 움직임 = 9/29 판을 되돌린 `dev` `67efcbc`, 지도 탭 = 10/1 밤 판). 다시 처음부터 찾지 않는다.
2. **재현·대조.** 불만 하나가 오면 리드가 같은 장면을 재현해 기준판과 같은 순간으로 나란히 보고, 무엇이 다른지 말로 짚는다. 불만을 다른 목표로 번역하지 않고(9/30 “그냥 25년 리캡 보는 느낌”을 “멈춤이 거의 일상 = 실패”로 옮겨 빗나감), 불만의 범위만 고친다(여러 해 불만으로 한 해까지 바꾼 9/30). 레퍼런스 조사는 후보 재료지 원인 증명이 아니다.
3. **하나만.** 바꿀 것 하나를 리드가 정한다. 담당은 그 하나만 구현하고, 폰에서 기준판 ↔ 후보를 바로 바꿔 볼 DEBUG 칩을 붙인다. 사용자 눈에 보이는 변화(움직임·모양·색·시간·개수) 중 브리프에 이름 붙지 않은 것은 담당이 정하지 않고 돌아온다.
4. **리드가 먼저 본다.** 리드가 정상 속도로 기준판과 나란히 보고 나아졌을 때만 사용자에게 간다. 숫자는 결함을 잡는 데 쓰고 좋아졌는지는 보고 판단한다. 사용자가 좋아한 것이 달라지면 바꾸기 전에 묻는다. 사용자에게는 추천 하나, 전후 한 장, 폰 칩.
5. **새 기준판.** 사용자가 좋다고 하면 그 판이 새 기준판이다. 한 바퀴는 30–40분 크기로 자른다.

- 장면을 새로 열 때와 문서를 크게 고칠 때 시키지 않아도 그 주제의 사용자 원문을 다시 모아 대조한다(“내 원문들 좀 모아서 핵심을 가져가봐 … 이런거 자꾸 내가 시키지 않아도 해주면 좋겟는데”, 10/1). 원문 모음은 세션 기록의 user 메시지로 갱신한다. 문서를 줄일 때 감성 기준과 감상 원문은 줄이지 않는다(“문서 줄일때 감성은 줄이지 않게 조심해줘”). 새 조사·후보판보다 이미 나온 재료를 엮어 추천을 만든다(“이미 던져진 감성+재료들이 무더기야 … 잘 해석하고 조합하거나”).
- 같은 영역을 잘 이해한 담당이 있으면 그 담당에게 이어서 맡긴다(“에이전트도 잘 알아듣는 애 생기면 이어서 시켜도 돼”, 10/1).

## 검증과 기록

- PRODUCT의 [감성 기준](record/PRODUCT.md#구현-단계와-무관하게-지킬-감성)을 구현 중에도 지킨다. 화면 역할·주요 조작이 바뀔 때와 결과를 보여 주기 전에 대조하고, 담당에게 넘길 때 그 화면의 이유·보호할 경험·미확인 판단을 함께 준다.
- 연출을 맡길 때는 볼 장면과 이어져야 할 관계, 보존할 것과 바꿀 수 있는 것을 준다. 조사를 맡길 때는 돌려받을 판단 재료를 정하고 찾는 대상·방법은 정하지 않는다([화면 규칙](record/PRODUCT.md#screen-rule)).
- 구현 검사 통과, 실제 동작, 사용자 체감 판정을 구분한다. 실제 지도·사진·조작감이 기준이면 build나 mock으로 완료 처리하지 않는다. 결함 주장은 관찰 사실과 원인 추정을 나눈다.
- 실행·영상으로 판단하는 작업은 소스 판본·설치본·입력·실행 ID·검사·영상의 대응을 그 작업의 QA 기록 한 곳에 둔다.
- 새 현황판·계획·작업 기록 파일을 만들지 않는다. 결정·계약·위험 경계가 바뀌면 PRODUCT·CURRENT를 고치고, 증거는 QA 폴더에 둔다. 끝난 일은 RETRO에 한두 줄로 줄이고 지운다. 미룬 항목은 원문·다시 꺼낼 조건과 함께 PRODUCT [1.0 뒤로 미룬 것](record/PRODUCT.md#after-v1)에 둔다.
- 결정 라벨은 사용자 확정 / 선호 / 권고안 / 검증 대기 / 구현 결정 / 대체됨을 구분하고, 모델 제안을 사용자 확정으로 올리지 않는다. 문서 정비는 제품 진척으로 세지 않는다.
- 규칙이 쌓이지 않게 한다(“규칙 기존에 정햐진게 너무 쌓이진 않는지는 조심하자”, 9/28). 새 규칙은 낡은 규칙을 고치거나 지우는 쪽을 먼저 본다.
