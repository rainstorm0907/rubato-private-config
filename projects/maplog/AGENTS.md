## 작업 안전

- 실행 승인은 현재 사용자 요청과 CURRENT 단계로 판단한다. 논의·점검·문서 반영이나 방식 제안을 제작 승인으로 넓히지 않는다.
- 여러 세션이 같은 작업 트리를 쓴다. 쓰기 직전 대상 파일과 diff를 다시 보고, 외부 변경이 생겼으면 그 파일 쓰기를 멈춘다. 무관한 파일을 고치거나 되돌리지 않는다.
- 담당은 자기 worktree에 커밋하고 리드가 `dev`에 합친다. push·reset·clean·revert와 다른 세션 변경 정리는 하지 않는다.
- 시뮬레이터는 고정 세 대(`iPhone 17 Pro`·`maplog-real`·`maplog-work`)만 쓰고 만들거나 지우지 않는다. 브랜치·worktree·빌드 폴더·시뮬·정리 규칙은 `/Users/wooojin/Downloads/maplog-qa/tools/BRIEF-ENV.md`에 있고 담당 브리프에 넣는다.
- 사용자 판단용 QA는 `/Users/wooojin/Downloads/maplog-qa/<날짜-작업>/`에 둔다. 키·실사진·사용자 좌표를 저장소에 넣지 않는다.

## 한 작업을 닫는 흐름 (사용자 2026-09-30 “일하는 방식부터 똑바로 확립해”)

사용자는 느낌을 준다. 원인 찾기·기계 확인·통합 검수는 리드 몫이다(“내가 주는건 느낌이고, 그건 어떻게 만들어나갈지는 너가 잘 고찰해봐야하는거야”). 느낌(원문) → 리드가 실제 장면 재현 → 원인 가르기 → 취향·손해·범위만 함께 결정 → 담당 수정·회귀 검사 → 리드가 `dev` 통합본 검수 → 사용자 감상.

- 불만을 다른 목표로 번역하지 않는다. 9/30 “그냥 25년 리캡 보는 느낌”(`6920e7c2`)을 리드가 “멈춤이 거의 일상 = 실패”로 옮겨 세 설계가 빗나갔다. 레퍼런스 조사는 후보를 찾는 재료지 원인 증명이 아니다(10/1 빌드 7 흰 테).

- 새 조사·후보판을 늘리기 전에 이미 나온 감성과 재료를 해석해 엮는다(“이미 던져진 감성+재료들이 무더기야 … 잘 해석하고 조합하거나”, 10/1). 조사가 돌아오거나 새 기능·장면을 열 때마다 리드가 원문·진단·조사를 종합해 조합 하나로 만들고(“앞으로 이렇게 종합하는 과정이 레퍼런스 조사 회수라던가 새로운 기능이라던가 계속진행되면좋겠어”, 10/1), 사용자에게는 추천 하나와 전후 한 장을 보인다.

## 검증과 기록

- PRODUCT의 [감성 기준](record/PRODUCT.md#구현-단계와-무관하게-지킬-감성)을 구현 중에도 지킨다. 화면 역할·주요 조작이 바뀔 때와 결과를 보여 주기 전에 대조하고, 담당에게 넘길 때 그 화면의 이유·보호할 경험·미확인 판단을 함께 준다.
- 연출을 맡길 때는 볼 장면과 이어져야 할 관계, 보존할 것과 바꿀 수 있는 것을 준다. 조사를 맡길 때는 돌려받을 판단 재료를 정하고 찾는 대상·방법은 정하지 않는다([화면 규칙](record/PRODUCT.md#screen-rule)).
- 구현 검사 통과, 실제 동작, 사용자 체감 판정을 구분한다. 실제 지도·사진·조작감이 기준이면 build나 mock으로 완료 처리하지 않는다. 결함 주장은 관찰 사실과 원인 추정을 나눈다.
- 실행·영상으로 판단하는 작업은 소스 판본·설치본·입력·실행 ID·검사·영상의 대응을 그 작업의 QA 기록 한 곳에 둔다.
- 새 현황판·계획·작업 기록 파일을 만들지 않는다. 결정·계약·위험 경계가 바뀌면 PRODUCT·CURRENT를 고치고, 증거는 QA 폴더에 둔다. 끝난 일은 RETRO에 한두 줄로 줄이고 지운다. 미룬 항목은 원문·다시 꺼낼 조건과 함께 PRODUCT [1.0 뒤로 미룬 것](record/PRODUCT.md#after-v1)에 둔다.
- 결정 라벨은 사용자 확정 / 선호 / 권고안 / 검증 대기 / 구현 결정 / 대체됨을 구분하고, 모델 제안을 사용자 확정으로 올리지 않는다. 문서 정비는 제품 진척으로 세지 않는다.
- 규칙이 쌓이지 않게 한다(“규칙 기존에 정햐진게 너무 쌓이진 않는지는 조심하자”, 9/28). 새 규칙은 낡은 규칙을 고치거나 지우는 쪽을 먼저 본다.
