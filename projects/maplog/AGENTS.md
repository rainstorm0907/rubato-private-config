# Maplog 작업 안내

## 시작과 문서 권위

항상 [record/CURRENT.md](record/CURRENT.md)와 [record/PRODUCT.md](record/PRODUCT.md)만 읽고 시작한다.
CURRENT는 구현 사실·승인 상태, PRODUCT는 현재 제품 정의·감성 기준·보호 조건·열린 판단을 맡는다.
지난 과정은 [record/RETRO.md](record/RETRO.md)에 한 번 요약돼 있고, 문서 목록은 [record/README.md](record/README.md)에 있다.
화면을 만들거나 크게 고치는 작업, 핀·카드 같은 부품의 모양을 새로 찾는 작업은 PRODUCT의 [화면 규칙](record/PRODUCT.md#screen-rule), `~/.agents/skills/frontend-ux-router/SKILL.md`(전역 CLAUDE.md가 정한 화면 제작 주담당 스킬), [code/DESIGN.md](code/DESIGN.md)(해당 세부 계약 포함)를 읽고, 담당 브리프에도 넣는다.

우선순위: 현재 사용자 요청 → PRODUCT의 현재 계약과 CURRENT의 사실·승인 → 해당 결정 원문·상태 → 관련 화면 계약 → 실제 검증 기록 → 과거 계획.
충돌이 발견되면 요약으로 사용자 결정을 덮지 말고 원문을 확인한다.
확정인 것은 사용자가 원하는 방향이지 모든 세부 방식이 아니다. 논의·구현 중 현재 판단에 영향을 주는 문장은 사용자가 실제 원한 것인지, 당시 상황에 한정된 말인지, 모델이 덧붙인 해석인지 대조한다. 충분히 이해하기 전에 새 확정문으로 갈아 끼우지 않는다. [PRODUCT의 적용 규칙](record/PRODUCT.md#문장을-적용하기-전에-되짚는다)을 따른다.
제품 방향은 2026-08-30 분기점 이후를 기준으로 한다. 이전 코드는 폐기물이 아니라 선택적으로 참고·재사용할 자산이다. 이전 문서는 RETRO 요약만 남기고 지웠다(원본은 git 기록).
옛 단계표·ops 큐·세션 역할표를 현재 실행 지시로 사용하지 않는다. git 기록에서 본 옛 문서의 “현재·다음·정본”은 당시 의미다.

## 승인과 작업 안전

- 실행 승인은 CURRENT 맨 위 최신 승인 블록과 현재 사용자 요청으로 판단한다. 이 안내에 시점별 승인 범위를 복제하지 않는다. 상태 점검·논의·문서 반영, 담당자 구성 승인이나 화면 작업 방식의 제안을 구체적인 제작 승인으로 넓히지 않는다. 중단된 구현 자산이나 과거 단계표는 기준안·재개 권한이 아니다.
- 여러 세션이 같은 dirty working tree를 쓴다. 쓰기 직전 대상 파일과 diff를 다시 확인하고, 작업 중 외부 변경이 생겼으면 해당 파일 쓰기를 멈춘다.
- 무관한 파일을 수정·되돌리지 않는다. commit·push·reset·clean·revert나 다른 세션 변경 정리는 하지 않는다.
- 기존 코드 통째 이식·재작성은 자동 선택이 아니다. 재사용 후보의 실제 의존과 계약을 확인한다.
- 시뮬레이터는 고정 세 대(`iPhone 17 Pro`·`maplog-real`·`maplog-work`)만 쓰고 만들거나 지우지 않는다. 브랜치·worktree·빌드 폴더·시뮬·정리 규칙은 `/Users/wooojin/Downloads/maplog-qa/tools/BRIEF-ENV.md`에 있고, 담당 브리프에 넣는다.
- 사용자 판단용 QA는 /Users/wooojin/Downloads/maplog-qa/<날짜-작업>/에 둔다. 키·실사진 원본·임시 QA 데이터를 저장소에 추가하지 않는다.

## 검증과 기록

- PRODUCT의 [감성 기준](record/PRODUCT.md#구현-단계와-무관하게-지킬-감성)을 구현 중에도 유지한다. 화면 역할이나 주요 조작이 바뀔 때와 결과를 보여주기 전에 대조하고, 작업을 넘길 때 해당 화면의 이유·보호할 경험·미확인 판단을 함께 전달한다. 기능 연결 성공이 감상 경험을 대신하지 않는다.
- 연출을 맡길 때는 볼 장면과 그 안에서 이어져야 할 관계를 먼저 설명하고, 보존할 것과 바꿀 수 있는 것을 붙인다. 보완 지시도 그 관계로 돌아가며 ‘더 좁게’ 같은 국소 조건을 새 목적으로 삼지 않는다. 전체로 확장하기 전 대표 연결이 의도한 관계를 실제로 보여주는지 살피되, 첫 렌더마다 사용자 승인을 받거나 정상 속도 감상을 정지 화면으로 대신하지 않는다. 조사를 맡길 때는 도구가 아니라 돌려받을 판단 재료를 정한다 — 표현 방향이면 물음별로 묶은 선별 시각 사례와 각각 왜 좋은지([화면 규칙](record/PRODUCT.md#screen-rule)), 사실 확인이면 출처·날짜·상충 근거.
- 구현 검사 통과, 실제 동작 통과, 사용자 체감 판정을 구분한다. 결함 주장은 관찰 사실과 원인 추정을 나누고, 검사 자체의 호출 순서·입력·의미 있는 차이부터 대조한다. 문서 정비는 제품 진척으로 세지 않는다.
- 실제 지도·사진·조작감이 기준이면 build나 mock만으로 완료 처리하지 않는다.
- 실행·영상으로 판단하는 작업은 제작자가 해당 소스 판본, 빌드·설치본, 입력·옵션, 실행 ID, 검사·영상의 대응을 기존 QA 기록 한 곳에서 관리한다. 시각이나 현재 소스 해시만으로 옛 설치본과의 동일성을 단정하지 않는다. 검토자는 주장에 필요한 대응을 확인하고, 리드는 핵심 근거와 목적을 대조한다. 바뀐 부분은 새 결과로 재확인하며 수정 없는 재녹화에 재빌드를 강제하지 않는다.
- 다음 준비가 필요한 이유는 그것 없이 깨지는 사용자 행동이나 데이터로 설명한다. 기존 단계표만으로 선행 작업을 늘리지 않는다.
- 별도 작업 기록 파일은 만들지 않는다. 사용자 결정·공통 계약·회귀 위험 경계가 바뀌면 PRODUCT·CURRENT에 반영하고, 검증 근거는 QA 폴더에 둔다. routine 수정은 task final로 닫는다.
- 결정 라벨은 사용자 확정 / 현재 릴리스 확정 / 선호 / 권고안 / 검증 대기 / 구현·QA 결정 / 대체됨을 구분한다. 모델 제안을 사용자 확정으로 올리지 않는다.
- 새 CURRENT·계획 문서를 만들지 않는다. 두 정본만 갱신하고, 지금 필요한 증거만 QA 폴더로 연결한다.
- 지난 진행은 남겨 두지 않는다. 끝난 일은 [record/RETRO.md](record/RETRO.md)에 한두 줄로 요약하고 CURRENT·PRODUCT에서 지운다(원본은 git 기록). 결과 보고서 맨 위의 완료 범위·실패·미확인은 최신 근거와 맞춘다. 정정을 뒤에만 붙여 옛 완료 선언을 현재로 남기지 않는다. 예산 내 반환이나 일부 검사 통과를 전체 완료로 올리지 않는다. 미룬 항목은 직접 표현·재개 조건을 PRODUCT에 보존하고 제외 기능([이번 출시에서도 안 하는 것](record/PRODUCT.md#not-this-release))을 되살리지 않는다.
- 위임은 현재 런타임과 승인된 역할을 따른다. 7월 ops의 모델명·세션·대기열은 현재 실행 상태의 증거가 아니다.
